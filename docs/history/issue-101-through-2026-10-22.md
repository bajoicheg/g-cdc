## Development contract for 3.0.0

Use a lightweight hybrid: **specification-driven development + a few behavior/acceptance scenarios + risk-based verification + selective TDD**.

Here SDD means **specification-driven development**. Subagent-driven development is an execution option, selected separately when independent tasks justify its overhead.

1. Start from a short change contract: intended observable result, relevant constraints, changed interfaces/invariants, risk and acceptance evidence. Scale it to the change; a clear reversible correction does not require a new lengthy design or repeated owner approvals.
2. Express the important user/operational outcomes as concise acceptance scenarios (BDD-style). Formal Gherkin files or another framework are optional and justified by practical value.
3. Use TDD where a failing example materially reduces uncertainty: complex logic/algorithms, critical invariants, authentication/authorization, ownership and external-effect controls, migrations, or a reproducible defect. For a bug, prefer one reproducer/regression that demonstrates the observed failure and its correction.
4. Low-impact reversible documentation, formatting and straightforward changes can use direct implementation followed by focused validation. Do not add tests that mirror code, assert incidental implementation structure, duplicate existing evidence, or count prose phrases as proof of runtime behavior.
5. Every new check must identify a distinct requirement, observed defect or plausible failure mode. Test count and coverage percentage are diagnostic metrics, never the reason to multiply tests.
6. Keep one minimal evidence path per independent risk: changed behavior checks, relevant integration/contract check and required platform/artifact proof. Use behavioral RED/GREEN traces for material agent/control behavior changes; do not mechanically require pressure scenarios for every prose edit.

## FAST / MEDIUM / FULL

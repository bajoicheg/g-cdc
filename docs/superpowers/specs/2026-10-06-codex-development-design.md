CDC: разработка в Codex, платформенные проверки в GitHub
Техническая схема для рассмотрения. 6 октября 2026 года.

1. Согласованная цель

Пользователь выбрал разделение: разработка и переносимые проверки выполняются в Codex; GitHub хранит код и выполняет необходимые платформенные проверки. Основная цель — уменьшить расход Codespaces и риск исчерпания его общего месячного лимита, сохранив проверяемость изменений. Это целевая архитектура, а не заявление о завершённой миграции.

2. Фактическая исходная точка

CDC 2.11.6 уже предпочитает Codex для переносимых проверок. Его адаптер scripts/codex_cloud_cli.py использует официальную CLI и режим COMPUTE_ONLY. Этот режим запрещает редактирование, commits, push и применение diff. Следовательно, переход к облачной разработке требует нового контракта исполнителя; смена названия backend или отключение запрета недостаточны.

Текущий managed_host_bridge управляет изолированным рабочим деревом, владением проекта, проверкой результата, публикацией и освобождением владения. Его существующие гарантии должны сохраниться. Проверенный маршрут требует нативного Git-доступа из управляющего окружения. При переносе нельзя считать доступ Work-коннектора доказательством доступа Codex или наличия Git-credentials.

Текущие официальные инструкции Codex описывают переиспользуемые cloud environments: отдельные задачи получают собственные рабочие пространства. Документация прежнего Cloud-маршрута теперь обозначена Legacy. Совместимость нашей CLI 0.160.0 с актуальными средами и экспортом результата должна быть проверена, а не предположена.

3. Рекомендуемая архитектура

Управляющая задача CDC работает в проверенной облачной среде Codex. Постоянно запущенный Codespace не является обязательным компонентом целевой схемы. GitHub остаётся источником исходных данных, координации и проверенных commits.

Облачный разработчик получает канонический репозиторий, исходный SHA, разрешённые пути, критерии приёмки и конечный бюджет. Он меняет собственное изолированное дерево. Единственный интегратор проекта проверяет результат и публикует его. Независимые проекты могут иметь независимые управляющие задачи; изменения одной области одного проекта сохраняют существующую координацию владения.

COMPUTE_ONLY сохраняется для проверки замороженного кандидата. Для разработки вводится отдельный контракт с исходным SHA, идентификатором задачи, разрешёнными путями и доказуемым результатом. Нельзя расширять права старого контракта незаметно для потребителей.

В первом этапе применяется один облачный разработчик на проект. Увеличение параллельности выполняется после подтверждения расхода, корректности восстановления и интеграции. Это не обещает неограниченную параллельность провайдера.

4. Возврат результата и публикация

До запуска фиксируются намерение, фактическая среда, исходный SHA и резерв бюджета. Потерянный ответ на запуск означает поиск уже созданной задачи, а не повторный запуск.

Результат включает базовый SHA, полный patch или commit/tree, список изменённых путей, команды проверок, exit codes, логи и hashes. Способ экспорта выбирается только после проверки доступного официального интерфейса. Произвольное извлечение внутренних API и копирование credential-файлов не допускаются.

Интегратор сверяет базу и разрешённые пути, проверяет результат в изолированном дереве и публикует при неизменившемся исходном HEAD. При конфликте выполняется контролируемая новая интеграция с повторной проверкой. READY провайдера не означает PASS. Перед завершением подтверждаются опубликованный SHA, checkpoint, освобождённое владение и отсутствие потерянной внешней задачи.

5. Какие проверки остаются в GitHub

В Codex переносятся реально исполнимые сборка, unit/regression-тесты, lint, схемы и детерминированные контракты. GitHub выполняет необходимые Windows-проверки Switcher и других Windows-проектов, а также платформенные и release-проверки, которые облачная среда не доказала.

Сборка Windows-приложения из иной ОС не доказывает работу Win32 hooks, Edit/RichEdit, UI Automation и пользовательских приложений. Сборка APK не доказывает работу устройства, эмулятора или Doze. Невыполненные проверки остаются NOT_RUN.

Для публичных репозиториев стандартные GitHub-hosted runners бесплатны по compute. Это не означает бесплатность всех типов исполнителей и хранения артефактов. Закрытые проекты не нужно открывать для использования Codex; доступ устанавливается отдельно для соответствующей среды и репозитория.

6. Расход и лимиты

Codespaces, Actions и ChatGPT/Codex учитываются раздельно. Локальные обращения к Codex и cloud-задачи расходуют общее allowance плана; могут действовать недельные лимиты. После исчерпания включённого использования продолжение может потребовать кредитов. Перенос не гарантирует меньшую полную стоимость без измерения фактической нагрузки.

Перед каждой задачей устанавливаются конечные пределы времени, количества попыток и параллельности. Ошибка учитывается в расходе; новая попытка требует конкретного исправления или подтверждённого восстановления сервиса. UNKNOWN не освобождает резерв. Автоматические повторные запуски и переход к платному fallback без установленного бюджета не разрешаются.

Внутренний ledger хранит задачи, попытки и резерв; фактическое allowance и оплачиваемый расход сверяются с dashboard провайдера. Ledger не выдаёт приблизительные оценки за реальный остаток подписки. Временные Codespaces останавливаются после освобождения владения; хранение остановленного Codespace учитывается отдельно.

7. Последовательность внедрения

Первый этап: завершить актуальное обновление Switcher до CDC 2.11.6 и убедиться, что его публикация и освобождение владения подтверждены.

Второй этап: в g-cdc проверить актуальное облачное окружение и официальный способ запуска, возврата результата и нативной Git-публикации. Подготовить контракт облачного разработчика и управляющего окружения. Сохранить старый COMPUTE_ONLY для замороженных кандидатов.

Третий этап: пилот на g-cdc с одной ограниченной процессной задачей. Пройти полный цикл без постоянно работающего Codespace: получение базы, изменение, проверки, проверка результата интегратором, публикация, освобождение владения и восстановление после прерывания.

Четвёртый этап: сравнить реальный расход пилота с прежним маршрутом; внедрить версионированный CDC и распространять его на проекты последовательно. Для каждого проекта подтвердить привязку среды и доступ, определить переносимые и платформенные gates, затем убрать зависимость управляющего процесса от Codespaces.

8. Критерии приёмки

Пилот выполняется без постоянно запущенного GitHub Codespace. Опубликованный результат имеет проверяемую базу и затрагивает только разрешённые пути. Повторное наблюдение не создаёт новую задачу. Исходный HEAD drift предотвращает слепую публикацию. Прерывание, потеря ответа, исчерпание бюджета и конкурирующее владение оставляют восстанавливаемое состояние. Платформенные gates не заменяются переносимыми. Доступ и фактический расход подтверждены; секреты не попадают в результат и журналы.

9. Границы этого документа

Схема не внедрена. Не изменены billing, публичность репозиториев, разрешения приложений и политика старого COMPUTE_ONLY. Конкретный интерфейс нового контракта и версия следующего CDC определяются после проверки актуального репозитория g-cdc и пилотного облачного маршрута. До этого перенос всех проектов не объявляется завершённым.

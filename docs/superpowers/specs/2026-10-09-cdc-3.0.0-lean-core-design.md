# CDC 3.0.0 lean execution core

Combined recovery example: a stale/incomplete/source-drifted probe with an
existing external operation returns RECONCILE while preserving that original
operation identity in the result. It cannot lose the operation or authorize
replay merely because fresh reconciliation is required first.

Status: source development; issue #101 is the accepted baseline. No release,
installation, consumer adoption, or Fleet rollout is authorized by this work.
Develop under the independent released CDC 2.12.1 runtime. The 2.13.0 Cloud
fast-start work remains a separate integration dependency until qualified.

## Problem and outcome

Resume currently requires several separate evaluator commands and reading a
large instruction file. Quality, repeat-cycle, and evidence-reuse contracts
exist but are not presented as one development decision. Operation reporting
does not have a typed measurement contract. CDC 3.0.0 joins these existing
contracts, gives one executable read-only entry point, and makes the default
instructions small enough to resume without re-reading history.

## Required behavior

1. A short specification and behavior acceptance examples precede meaningful
   changes. Select TDD for complex logic, critical boundaries, and reproduced
   bugs. Direct reversible text/layout edits receive focused validation.
2. One development assessment composes the existing quality floor, repeat
   discipline, and evidence reuse. Core, authentication, ownership, dangerous
   migration and external-effect gates remain FULL. A lower-cost choice never
   changes authority or removes an independent mandatory gate.
3. `python -B scripts/cdc.py resume --capsule FILE --probe FILE` assesses the
   existing capsule and fresh probe, producing exactly one typed next action.
   A stale/different/incomplete observation reconciles; an existing external
   operation is reconciled before another start; blocked health or a recorded
   pause waits. The command never executes free-text commands, creates a
   lease, starts compute, launches agents, or writes control state. It is the
   executable observation/routing entry; effects stay with the existing
   authorized runtime. Qualified Cloud fast-start must be reused, not cloned.
4. The default skill is a compact routing/core document. Historical detail
   remains in phase references. Only references needed by the current phase
   are loaded. Current state is a capsule/checkpoint, not another ledger.
5. Compatible low-risk changes may share one candidate and aggregate check.
   Risk floors and required isolated/platform/release checks still apply.
   Urgent changes may remain separate. Parallel executors require independent
   scopes and existing budget admission; one integrator owns assembly.
6. Russian chat, English source documents, one fresh Moscow timestamp per
   user command. Completed-operation suffixes use rounded minutes; measured
   or defensibly estimated tokens have provenance, unknown tokens are omitted.
   Delivery measurements retain unknown values and observed phase durations;
   comparisons report observed values, never unmeasured savings or fabricated
   defect improvements. Existing budget events remain the accounting source.

## Acceptance examples

| Given | When | Then |
|---|---|---|
| Matching fresh capsule/probe | resume | one RESUME action referring to checkpoint/task |
| Old SHA, changed policy/lease, incomplete probe | resume | one RECONCILE action, no execution authority |
| Recorded external operation | resume | RECONCILE_EXTERNAL, preserving its identity |
| Recorded blocker/recovery health | resume | WAIT or recovery reconciliation before continuation |
| Core risk with FAST requested | assess development | effective FULL, mandatory gates retained |
| Repeat without new input or justification | assess development | rejected by existing cycle contract |
| Unchanged relevant evidence inputs | assess development | evidence may be reused at its original SHA |
| Unknown token observation | report | `(N мин)` with no placeholder |
| Two dependent tasks or insufficient agent budget | execution strategy | single executor or WAIT, no start |
| Independent compatible tasks with admitted budget | execution strategy | bounded recommendation, one integrator |

## Boundaries and release path

This branch implements the independent 3.0.0 baseline first. It does not copy
unmerged 2.13.0 snapshots, mutate held leases/guards, change consumer pins,
reset quotas, deploy, or publish a release. Version and release metadata stay
at the released baseline until a candidate is assembled and bound correctly.
The initial frozen source candidate then uses 3.0.0 labels and candidate status,
bound to its actual package tree and the independent 2.12.1 driver. Bootstrap
supports exactly the next stable major with zero minor/patch as well as next
minor/patch; it preserves all independent base and release gates. This is
structural candidate support, never major-release or adoption permission.
The new-project adapter template permits the 3.x line. Existing archived/live
adapters with an exclusive 3.0.0 ceiling remain installation-incompatible until
an explicit qualified migration; their recorded restrictions are preserved.
Required final bootstrap/package/compatibility/fault/archived-consumer/CI
checks remain release gates. Archived-consumer tests are not live rollout.

The archived-consumer gate validates each original policy and checkpoint
binding against the independently pinned development driver. A ceiling exactly
equal to the next stable major must still reject the installed candidate. For
offline compatibility only, validate a detached in-memory copy with the next
major ceiling and its corresponding checkpoint policy digest. Preserve every
other field and the original archive bytes. Report original installation
incompatibility separately from migration-fixture compatibility; neither result
authorizes adoption or a policy write. Other validation failures, stale policy
bindings, different ceilings and non-major transitions fail the gate.

3.0.x patches follow observed compatible defects. 3.1 adds init/migrate and
project presets; 3.2 adds measured adaptive allocation; 3.3 adds release/adopt
automation and rollback. None grants live Fleet rollout in this session.
